# 设计说明：角色特长与技能库

状态：**a 阶段已落地（协议 §7），b/c 未实现**　实际版本：0.11.0 起　日期：2026-11-27（0.12.1 校对）

> 已实现的部分：协议里列出执行特长 `backend` / `data` / `general` 与校验特长 `functional` / `security` / `general`，并要求 `verifier_specialty ≠ specialty`、**没有验收条目的特长不得使用**、汇总要报特长。
> 未实现的部分：本文 §3 的 `presets/specialties.json`、§6 的白名单与哈希校验、设置页的特长管理。
> **注意**：仓库里**没有** `presets/` 目录，特长目前是硬编码在协议文本里的，不是从 JSON 读的。下面的数据结构是设计，不是现状。

---

## 1. 要解决什么 / 不解决什么

**要解决**：同一角色在不同领域的产出质量差异很大。一个"执行工程师"做后端接口和做数据清洗，需要的能力、工具、验收口径完全不同。用一个通用角色提示词覆盖所有领域，结果是验收标准只能写得很空泛。

**不解决**（明确排除，避免过度设计）：

- 不解决"角色头衔带来的专业性"。改个名字不会让模型更会写 SQL。
- 不做运行时技能市场/在线拉取。
- 不做跨 run 的技能学习（无记忆）。

**核心判断**：特长只有在携带**可运行验收标准**时才有价值；否则它只是提示词装饰。因此本设计中，一个没有 `acceptance` 的特长条目**不允许生效**。

---

## 2. 概念模型

```
角色（role）        固定 5 种：requirement_gate / chief / pm / worker / verifier
  └─ 特长（specialty）  每个角色可挂 N 个，按任务域选择
       ├─ when          什么任务该用它（选型依据）
       ├─ skills[]      技能名（引用，不内联内容）
       ├─ tools[]       可选，该特长需要的工具子集
       └─ acceptance[]  该特长的验收口径（必填，否则条目作废）
```

**关键约束**：

1. 一个任务只能指派**一个**执行特长。需要多域能力时拆任务，不要叠加。
2. 校验特长与执行特长**必须不同**（避免"自己人查自己人"）。
3. 特长只在 `worker` 与 `verifier` 上生效（幕僚长/PM 是调度与翻译，加特长收益接近零、只增 token）。

## 3. 数据结构

仓库内基线（**计划中，尚未建立**）：`presets/specialties.json`

```json
{
  "version": 1,
  "roles": {
    "worker": [
      {
        "id": "backend",
        "name": "后端工程",
        "when": "HTTP 接口、数据库读写、并发、鉴权",
        "skills": ["api-contract", "sql-tuning"],
        "acceptance": ["接口契约测试通过", "错误码与文档一致", "并发 100 次无 5xx"]
      },
      {
        "id": "data",
        "name": "数据处理",
        "when": "清洗、聚合、口径核对、报表生成",
        "skills": ["data-quality-check"],
        "acceptance": ["抽样 3 行可回溯到源数据", "合计等于明细求和", "空值与异常值有明确处置"]
      }
    ],
    "verifier": [
      {
        "id": "security",
        "name": "安全审查",
        "when": "涉及鉴权、输入校验、路径拼接、文件读写",
        "skills": ["threat-model"],
        "acceptance": ["每个外部入口有越权用例", "路径穿越用例被拒绝", "敏感字段未出现在日志"]
      }
    ]
  }
}
```

用户覆盖（可选，本机）：`~/.dsh-formation/specialties.local.json`

- 只允许**新增**条目与**覆盖同名条目的 acceptance**；
- 不允许覆盖 `skills`（技能引用必须以仓库基线为准，否则白名单失去意义）；
- 覆盖记录写进 `audit`，汇总时可见。

## 4. 注入方式

协议里只增加一段（不内联技能内容），约 8~12 行：

```
### 特长选型（仅 worker / verifier）
- 拆解时，由幕僚长为每个任务指定一个执行特长（见下表）；无法归类时用 `general`。
- 每个任务只允许一个执行特长，需要多域能力请拆任务。
- 校验特长必须与执行特长不同；安全相关任务强制指定 verifier=security。
- 子代理提示词里必须包含：特长的 acceptance 原文 + 需要加载的 skills 名。
- 汇总时报告：任务 → 执行特长 / 校验特长 / 验收是否覆盖。

可用特长：
worker:  backend(后端工程) · data(数据处理) · general(通用)
verifier: security(安全审查) · functional(功能校验) · general(通用)
```

**为什么只传技能名**：技能内容由 DSH 的 `skill` 工具在子代理会话中按需加载。协议里塞全文会让每轮多花几千 token，且技能更新后协议会滞后。

**token 预算（实测标定，0.12.1）**：协议段当前 **2344 字符 / 58 行**，粗估 1.5–1.9k token，每轮都算。特长段已包含在内。

- 加特长之前（0.9.x）约 1.2k 字符；
- 加入沟通循环 + 预算制 + 特长后涨到 2.3k；
- 再往上加就要警惕：协议越长，模型越可能只记住开头几段（Context Rot）。

以 worker=3、verifier=2 计，单次交付的模型调用成本远大于协议本身（每子代理约 25k token），所以协议长一点可以接受，但**不要超过 3k 字符**。

## 5. 选型规则

| 决策 | 谁做 | 依据 |
|---|---|---|
| 任务属于哪个域 | 幕僚长 | 拆解时已看全貌，`when` 描述 |
| 具体执行特长 | 幕僚长 | 每个任务一个，写入任务清单 |
| 校验特长 | 幕僚长，但受硬约束 | 必须 ≠ 执行特长；安全类强制 security |
| 验收断言具体化 | PM | 把特长的 `acceptance` 翻译成可运行命令 |

**冲突处理**：

- 一个任务命中多个 `when` → 取**最具体**的一个；仍无法判断 → 标 `general` 并在汇总中提示"该任务未匹配特长"。
- 任务确实需要多域 → 拆成两个任务，各自一个特长（幕僚长负责）。
- 特长指向的技能不在白名单 → 该特长降级为 `general`，日志与汇总都标注，不阻塞交付。

## 6. 污染控制（三层）

技能是**可执行指令**，一份恶意 SKILL.md 能让校验员放水，而输出看起来一切正常。因此分三层控制：

### 6.1 来源层

- 只允许 `presets/skills.allowlist.json` 中登记的技能名。
- 白名单随仓库发布，人工审查后合并；**运行时不接受任何外部输入来源**。
- 未登记的技能名一律不注入。

### 6.2 版本层

```json
{ "api-contract": { "sha256": "…", "source": "presets/skills/api-contract/SKILL.md", "reviewed": "2026-11-27" } }
```

- 插件启动时对每个登记技能计算哈希，与白名单比对。
- 不匹配 → 该技能不注入，写日志（`warn`），不影响其它技能。
- 白名单文件本身被改动 → 视为不可信，整份特长功能降级为关闭，并在诊断页显红。

### 6.3 加载层

- 协议只出现技能**名**，不出现内容。
- 子代理需要时调用 `skill` 工具加载；加载发生在该子代理自己的上下文里，不污染父级。
- 校验子代理不加载执行特长用到的技能（避免同源思路）。

### 6.4 硬规矩

**运行时零网络**。插件当前不发起任何外部请求，这个性质必须保持——"对接在线技能库"等于在提示词供应链上开一个后门。

## 7. 与 DSH 现有机制的关系

| 需求 | 用什么 | 为什么不用别的 |
|---|---|---|
| 工具子集 | `agentPreset` | 现成的组合机制，不必自造 |
| 技能 | `skill` 工具 + SKILL.md | 平台已有加载器，重复实现会漂移 |
| 提示词 | `systemPrompt.section` + 装配钩子 | 已在用，扩展成本最低 |

**不新造**：不写自己的技能加载器、不写自己的工具注册表。

## 8. 失败模式与回退

| 失败 | 影响 | 回退 |
|---|---|---|
| 特长选错 | 执行者方向偏，校验打回 | 打回即回退到 `general` 重跑该任务，成本约 1 次会话 |
| 技能名不在白名单 | 该特长降级 | 降级为 general，日志标注 |
| 哈希不匹配 | 该技能不可用 | 仅该技能失效，其余照常 |
| 白名单被改 | 全部特长关闭 | 诊断页显红，协议回到无特长版本 |
| 协议过长导致模型忽略 | 特长不生效 | 汇总里要求报告特长使用情况，可从输出判断 |

**总开关**：**目前没有** `specialties.enabled` 这类开关（原设计有，实现时去掉了）。理由：a 阶段只是 5 行文本、不加载任何技能内容，关掉它省不到 token，反而多一条配置状态要维护。等 b 阶段真开始加载技能时再加。

## 9. 怎么证明它有价值

**不能只凭"看起来更专业"就下结论**。用同一条需求做 A/B：

| 组 | 配置 | 观察 |
|---|---|---|
| A | 无特长 | 基线 |
| B | 执行/校验各指定特长 | 对比 |

度量三项：

1. **首次校验通过率**（越高越好）
2. **返工轮数**（越低越好）
3. **单任务 token**（特长的成本）

判定：B 的首次通过率显著高于 A、且返工轮数下降，才认为有效。否则特长只是多花钱。

**建议样本量**：至少 10 个任务，且任务要跨域（接口/数据/文档），否则测不出差异。

## 10. 实施拆分

| 阶段 | 内容 | 风险 | 状态 |
|---|---|---|---|
| a | 协议注入特长名 + 验收约束 + 汇总要求报告特长 | 低，纯提示词 | ✅ 0.11.0 已做（硬编码在协议里，未读 JSON） |

| c | 设置页管理特长（增删改、启停） | 中，UI 工作量 | ⬜ 未做 |
| d | A/B 度量工具（记录每轮的特长与验收结果） | 需要跑真实任务 | ⬜ 未做 |

**建议下一步先做 d 的前置**：先跑 10 个真实任务，看 a 阶段的特长描述是否真的让验收更具体。如果没有，b/c 就是在给装饰品加基础设施。

## 11. 未决问题

1. **特长由谁维护**？纯手工写 JSON，还是允许从 DSH 已有 skills 目录自动发现候选？前者可控，后者省事但引入未审查来源。
2. **`tools[]` 要不要做**？工具子集需要 `agentPreset` 配合，而 `agentPreset` 的可用值我还没确认。
3. **特长能不能跨工作区共享**？当前配置是全局一份，特长是否也全局？还是按工作区覆盖？
4. **校验特长与执行特长"必须不同"**——如果任务本身就跨域（如"后端 + 安全"），是否允许 verifier 挂两个特长？我倾向不允许，改为拆任务。
