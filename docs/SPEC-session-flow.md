## 1. 状态机

```
IDLE
 └─(判型=交付类)→ ELICIT ──(用户选「开始实现」)→ REVIEW
                     ↑                              │
                     └──(还需要补充)───────────────┤
                                                    ▼
                                                  PLAN
                                                    │
                                                    ▼
                                                 DISPATCH
                                                    │
                                        ┌───────────┴───────────┐
                                        ▼                       ▼
                                     VERIFY ──(通过)→ ── SUMMARY → DONE
                                        │
                                   (打回)→ 重派该任务（有次数上限）
```

| 状态 | 拥有者 | 进入条件 | 退出条件 |
|---|---|---|---|
| IDLE | 根会话 | 会话空闲 | 判型为交付类 |
| ELICIT | 需求沟通官 | 判定需要沟通 | **只认**用户选「需求已经沟通完成，开始实现」，不设轮数上限 |
| REVIEW | 根会话 + 用户 | 设计书产出 | 用户确认 / 要求修改（回 ELICIT） |
| PLAN | 幕僚长 | 设计书已确认 | 任务清单产出且通过校验 |
| DISPATCH | 幕僚长 | 任务清单就绪 | 全部任务完成校验 |
| VERIFY | 独立校验 | 单个任务执行完成 | 给出 pass/fail |
| SUMMARY | 幕僚长 | 全部任务终态 | 输出汇总 |
| DONE | — | 汇总完成 | — |
| BLOCKED | 任意 | 触发阻塞条件（见 §5） | 用户介入或放弃 |

**关键新增：REVIEW**。v1 里设计书直接进 PLAN，这等于让模型自己确认自己。加一道人确认闸，因为设计书写错会让下游全错（0.8.1 踩过：漏减号，校验判通过）。

## 2. 消息契约

所有跨角色交接都是 JSON，带 `v` 版本号。字段只增不改，避免下游解析崩。

### 2.1 问题组（沟通官 → 根会话）

```json
{
  "v": 1,
  "round": 2,
  "intro": "还差三点才能定下来",
  "questions": [
    {
      "id": "q1",
      "text": "统计口径按含税还是不含税？",
      "why": "影响收入合计，两种口径差 6%",
      "options": ["含税", "不含税"],
      "multi": false,
      "default_if_skipped": "不含税（并标注）"
    }
  ],
  "can_finish": true,
  "finish_label": "需求已经沟通完成，开始实现"
}
```

约束：
- 每轮 `questions` ≤ 4。超过 4 个，用户会放弃。
- **没有 `max_rounds`**：轮数不设上限，收尾权只在用户手里（见 §3.3）。
- `can_finish=false` 时，仍要显示收尾选项，但标注「还有 N 项未定，将按默认值处理」——**永远不锁死用户**。
- `default_if_skipped` 必填：用户跳过任何问题，都有明确兜底。

### 2.2 用户答案（根会话 → 沟通官）

```json
{ "v": 1, "round": 2, "answers": { "q1": ["不含税"] }, "finished": false, "custom": "" }
```

`finished=true` 即用户选了收尾选项。

### 2.3 需求设计书（沟通官 → 幕僚长）

```json
{
  "v": 1,
  "goal": "…",
  "scope": { "in": ["…"], "out": ["…"] },
  "constraints": ["…"],
  "acceptance": ["运行什么 → 看到什么"],
  "assumptions": ["用户未回答，按默认值处理：…"],
  "open_risks": ["…"],
  "domain_hints": ["backend", "data"],
  "rounds_used": 3
}
```

`assumptions` 必须非空——用户跳过的问题全部落在这里，下游不得再猜。

### 2.4 任务清单（幕僚长 → 派发器）

```json
{
  "v": 1,
  "tasks": [
    {
      "id": "T1", "title": "…", "specialty": "backend",
      "priority": "P0", "depends_on": [],
      "acceptance": ["…"], "verifier_specialty": "functional"
    }
  ]
}
```

校验：
- 每个 task 必有 `specialty`（缺省 `general`）
- `verifier_specialty ≠ specialty`
- `|tasks| ≤ max_tasks`
- `depends_on` 必须无环（拓扑排序后按层派发）

`plan.json` 还要带上幕僚长申报的编制：

```json
{ "v": 1, "tasks": [ … ], "quota": { "worker": 2, "verifier": 2 }, "quota_rationale": "6 条任务、2 个方向，每方向 2 条串行" }
```

### 2.4.1 定编：设置是上限，插件钳制

设置里的 `worker` / `verifier` 是**并发天花板**，不是要照满派的人数。派发前调：

```
GET /api/quota?tasks=<条数>&directions=<方向数>&want_worker=<申报>&want_verifier=<申报>
```

返回里 **`granted` 才是准数**，`ceiling` 只是上限。

| 字段 | 含义 |
|---|---|
| `floor` | 硬下限：执行 `max(1, ceil(任务/6))`，校验 `max(1, ceil(任务/5))`（封顶到上限） |
| `granted` | `clamp(申报, floor, ceiling)`；未申报时**按下限给**（默认给满 = 鼓励空转） |
| `serialized` | 方向数 > 执行数，组内任务串行 |
| `over_ceiling` | 申报超过设置上限 → 这是唯一需要用户点头的情况 |
| `estimate_tokens` | 粗估成本，每子代理按 25k |

下限是硬的，**不因用户嫌麻烦而降低**：校验员被砍掉，`2297` 那类"错的总和也被判通过"的 bug 就会重现。

**确认策略：只在越界时打断一次。**

- `over_ceiling: false` → 钳制后直接派，**不打断用户**。一次交付拆成 4 批问 4 次，用户从第 3 次起只会乱点「是」，确认就成了橡皮图章。
- `over_ceiling: true` → 停，问一次，报清「需要几个 / 上限几个 / 预计多少 token」。用户不点头就按上限派、多余任务串行。
- 下限与「用户说加快」无关：加急只能砍并行方向数，不能砍校验。

### 2.5 载荷包（派发器 → worker）

```json
{ "v": 1, "worker": "W-1", "specialties": ["backend"], "tasks": ["T1","T2"], "skills": ["api-contract"] }
```

`skills` 为组内所有特长技能名的并集，去重。

### 2.6 校验结论（verifier → 幕僚长）

```json
{ "v": 1, "task": "T1", "passed": true, "checks": [{"name":"…","result":"pass","evidence":"…"}], "issues": [] }
```

`evidence` 必填：必须是自己跑出来的命令输出片段，不能是"我检查过了"。

## 3. 需求沟通循环（实现细节）

### 3.1 角色分工

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| 沟通官（子代理，可延续） | 生成问题组、判断是否够了、产出设计书 | 不直接接触用户、不写代码 |
| 根会话 | 中继：渲染问题、收集答案、回传 | 不替沟通官编问题 |
| 用户 | 选选项、写补充 | — |

### 3.2 一轮的完整时序

```
沟通官 ──问题组 JSON──► 根会话
根会话 ──ask_user_question(问题组 + 收尾项)──► 用户
用户 ──选择──► 根会话
根会话 ──答案 JSON──► 沟通官（sendMessage 到同一子代理）
沟通官 ──下一轮 或 设计书──► 根会话
```

### 3.3 终止条件

**只有一个：用户选中「需求已经沟通完成，开始实现」。**

- 不设轮数上限，不做「连续重复问题」检测——收尾权完全交给用户。
- 收尾选项**每一轮都必须存在**，且固定排在最后。这是用户唯一的退出开关，任何情况下不得隐藏。
- 若 `can_finish=false`（还有未定项），选项标注「还有 N 项未定，将按默认值处理」，但**仍然可选**。

理由：轮数是用户自己的成本，用户比任何阈值更清楚"问够了没有"。机器设上限反而会在没问清时强行收尾。

**残留风险**：沟通官可能反复问同一件事，用户不断点选项。缓解只有一条——收尾选项永远在，用户随时能停。不引入自动检测，避免误杀正常的多轮澄清。

### 3.4 保活与恢复

- 沟通官用 **continuable child**，跨轮复用同一会话
- 若用户中途离开（超时 30 分钟无输入）→ 状态停在 ELICIT，会话保持；用户回来继续
- 若进程重启 → 依赖 DSH 会话持久化冷恢复；**恢复后必须重新向用户确认"上次聊到哪"**，不能默认继续

## 4. 派发算法（补充 v1 第 5 节）

### 4.1 拓扑分层

有依赖的任务按层派发：第 1 层全部并行，完成后才进第 2 层。

### 4.2 载荷分配

```
G = 去重后的 specialty 数
W = granted.worker（`GET /api/quota` 返回的准数，不是设置里的上限）

若 G <= W:
   每组 ≥1 人；剩余 W-G 人按组内任务数加权
   若任务总数 < W：多余者转「异视角复核」，每任务最多 1 个
否则:
   每人承担 ceil(G/W) 个方向，组内串行
```

### 4.3 冗余人员的处理：改为「异视角复核」

任务数 < worker 数时，多余的人怎么办？结论：**只在能提供不同视角时才用，否则不拉起**。

**为什么同特长互查基本无效**：两个人拿同一份规格、看同一批文件、跑同一组命令，结论高度相关。它唯一能抓的是"对方偷懒漏跑了一条命令"——而校验结论本来就强制带证据，这条已被覆盖。

**什么才真的有信息增益**：复核者的特长与任务特长不同。例如后端任务由「安全审查」复核——它会问"有没有越权"，而功能校验员根本不会问这个问题。这是**不同的检查清单**，不是同一份清单再做一遍。

**规则**：

| 条件 | 行为 |
|---|---|
| 存在与被复核任务不同的 specialty | 拉起 1 个复核者，用该特长的 acceptance |
| 没有可用的不同 specialty | **不拉起**，直接省掉这次调用 |
| 复核上限 | 每个任务最多 1 个复核者（不是 2 个） |
| 结论作用 | 只进汇总的「附加观察」，**不改原 pass/fail** |

**收益判断**：它能提高"缺陷发现率"，但**不会**发现规格错误（双方共享同一份错误规格）——那仍然只能靠 REVIEW 闸。

## 5. 失败与回退

| 场景 | 处理 | 是否阻塞 |
|---|---|---|
| 用户中途放弃 | 状态停在 ELICIT，已收集内容保留 | 否 |
| 用户要求改设计书 | 回 ELICIT，`round` 不清零（避免重复提问） | 否 |
| 设计书字段缺失 | 根会话要求沟通官补一次；仍缺则按默认值填并标注 | 否 |
| 幕僚长拆解违规（如 verifier_specialty 相同） | 退回重拆一次；二次违规 → BLOCKED | 是 |
| 执行失败 | 同 worker 重试 1 次；仍失败 → 任务标 `failed`，继续其它任务 | 否 |
| 校验打回 | 重派该任务，最多 2 次；超过 → 该任务标 `escalated` | 部分 |
| **最近 5 个任务中 3 个 escalated** | 整单 BLOCKED，等人介入 | 是 |
| 预算超限 | 见 §6 | 是 |

**BLOCKED 的含义**：停止派发，输出当前进度与卡点，等人决定继续/放弃。**不允许自动无限重试**——那是最常见的烧钱方式。

## 6. 成本预算

| 阶段 | 估算 | 上限 |
|---|---|---|
| ELICIT | **每轮 1 次**子代理调用 | **无硬顶**（轮数由用户决定，见 §3.3） |
| REVIEW | 0 次（人确认，不调模型） | — |
| PLAN | 1 次 | 2 次（含重拆） |
| 每任务 DISPATCH | 1 worker + 1 verifier（PM 是常驻的，不按任务算） | 每任务重试 ≤ 2 |
| 异视角复核 | ≤1 次/任务，只在有不同 specialty 时 | — |
| SUMMARY | 1 次 | 1 次 |

**成本口径**：`GET /api/quota` 返回的 `estimate_tokens`（每子代理按 25k 粗估）才是交付前能看到的数。

> 早先版本写过「单次 run ≤ `max_tasks × 4 + 12` 次调用，超出即 BLOCKED」——**已废止**：这个数既不是插件能强制的（协议是文本），也会在 ELICIT 轮数放开后失效。现在只在汇总里报实际调用数，超了由人决定是否继续。

## 7. 可观测性

每次 run 在工作区里留 `_runs/<runId>/run.json`（**工作区资产，不写 `~/.dsh-formation/`**，与 §9.3 一致）：

```json
{
  "runId": "run-20261127-101500",
  "state": "DISPATCH",
  "rounds": 3,
  "quota": { "worker": 2, "verifier": 2, "granted": true },
  "tasks": [{"id":"T1","specialty":"backend","state":"verified","attempts":1}],
  "calls": 14, "tokensEstimate": 62000,
  "blocked": null
}
```

**页面上不显示这些**——页面只有设置，没有运行视图（这是既定取舍：不要"点一下就跑"的控制台）。

卡住时看两处：① `_runs/<runId>/run.json` 的 `state` 与 `blocked`；② 插件的「日志」区块（装配、开关、自测、异常都在里面）。

## 9. 子代理生命周期与数据保留

### 9.1 规则

| 阶段 | 需求沟通官 | 执行 / 校验 | 数据 |
|---|---|---|---|
| ELICIT | **常驻**（可延续，跨轮复用） | 不拉起 | 设计书草稿 + 对话轮次 |
| PLAN | **回收**（dispose） | 不拉起 | 设计书定稿 |
| DISPATCH | 已回收 | 按任务拉起，完成即回收 | `_runs/<runId>/` 产物 |
| 追加需求 | **重新拉起**，复用原会话 | 按需拉起 | 复用本地数据 |
| 会话归档/删除 | — | — | **同步删除** |

要点：**回收 ≠ 删除**。回收是卸句柄（省资源、停循环），数据仍在本地；重新拉起时接着用。

### 9.1.1 槽位复用（配额 = 并发上限，不是总人数）

`worker: N` 的含义是**同时最多 N 个 Worker 在跑**，不是整轮只起 N 个。

- 一批 Worker 的任务全部通过校验 → 立即 `dispose`；
- 空出的槽位**必须马上**交给下一批未派发的任务，不得等待、不得闲置、不得为"凑一批再上"而拖延；
- 校验员按单任务回收（校验完即 dispose）；
- 稳态是 N 个槽位一直流水，不是 N 个人从头跑到尾；
- 唯一例外：`depends_on` 未满足的任务不得进槽位，此时报告「槽位空闲 N 个，等待依赖 T?」。

### 9.1.2 冷恢复：已实测通过

探针 `POST /api/verify/resume` 走完整链路：子代理记住 `7391` → `dispose()` → `sendMessage` 唤醒 → 问它还记不记得。

结果：**记得**。所以"回收后按需重新拉起、复用原上下文"这条路成立，不需要为保上下文而常驻。

> 踩过的坑：round1 的 assistant 消息落盘晚于 `result` 返回。若按"最后一条 assistant"取回复，会读到 round1 的「已记住」，把成功判成失败。探针现以 assistant 条数做基线增量判断。

### 9.2 机制映射

| 动作 | DSH 能力 | 说明 |
|---|---|---|
| 回收 | `activation.dispose()` | 停循环、卸载注册。**已实测**：dispose 后会话日志仍在磁盘 |
| 重新拉起 | `subagents.sendMessage(parent, childId, …)` | 对已回收的直接子级做**冷恢复**，消息进入其 inbox 后唤醒 |
| 备选 | `ctx.agents.resume({ resumeSessionId })` | 按会话 id 重建 agent |
| 数据位置 | `_runs/<runId>/` + DSH 会话日志 | 产物在运行目录，上下文在会话日志 |

### 9.3 删除策略：绑定工作区，不自建级联

**原则：产物的生命周期 = 工作区的生命周期。**

- `_runs/<runId>/` 是工作区资产，跟随工作区的删除逻辑：工作区在，产物在；工作区移除，产物随之消失。
- 插件**不监听会话的归档/删除**，也不写任何级联删除——会话层面的事件不改变产物。
- 插件只负责运行过程中的**正常删除**：`tmp/` 收尾清空（已在协议里）。

这是有意的取舍：一次交付的产物属于工作区，不该因为某个会话被归档就消失；反过来，工作区没了，产物也没有存续的理由。

需要清理时用工作区层面的手段（手动删目录，或 0.9.3 已有的清理入口）。

## 10. 本版做出的决定（原待决问题）

| 原问题 | 结论 |
|---|---|
| 沟通终止条件 | **只认用户选择**「开始实现」，不设轮数上限、不做重复检测 |
| 设计书确认 | **强制 REVIEW 闸**，用户不点确认不进实施 |
| 判型由谁做 | 根会话自己判（省钱）；判不准按纯问答处理 |
| 4 方向 2 人如何分 | 每人 `ceil(G/W)` 个方向，组内串行 |
| 冗余人员 | **异视角复核**：特长必须不同才算数，否则不拉起 |
| 生命周期 | 沟通官在实现阶段回收、追加需求时冷恢复；回收不删数据 |
| BLOCKED 阈值 | **最近 5 个任务中 3 个 escalated** 即整单停 |
| 数据删除 | **跟随 DSH 规则，不自建级联**；`_runs/` 属工作区资产，会话删除不连带 |
